## Tasks from 2026-11-06 UX Discussion 3 (Sankalp — Aarti feedback relay)

Source: `docs/research/meetings/2026-11-06-sankalp-skills-ux-discussion-3.md`

> Sankalp walked Romit through Aarti's feedback on the prior design presentation. Core change: flip the setup flow order — start with "Create Skill Checklist" rather than building a flat skills library first. Also covers assignment UX, editing restriction, course mapping grid removal, and deferring the dashboard.

| # | Task | Persona | Surface | Priority | Notes |
|---|---|---|---|---|---|
| T_SC_17 | **DESIGN-REVIEW: Restructure admin setup flow — "Create Skill Checklist" first.** The current flow (add skills to flat library → create groups → assign) needs to be restructured. The new entry point is "Create Skill Checklist": admin gives the checklist a name, then adds skills within it. The skills library still exists as the underlying store, but the user journey starts from the named checklist container, not the flat list. Revise all admin setup screens to reflect this order. | Admin | Skills setup | P0 | Aarti directive via Sankalp: "The first step should be create a skill checklist. And within that shell, I'm adding all my skills." DESIGN-REVIEW before building — this restructures the entire admin onboarding flow. |
| T_SC_18 | **Admin assignment: "Assign to all students" as primary CTA.** When an admin has created a skills checklist, the primary action must be "assign to all students" — one-click assignment to all current and future students in the program. A secondary option allows cohort/group-filtered selection. Remove any design that implies per-student or per-skill individual assignment. | Admin | Skills assignment | P0 | Aarti (via Sankalp): "Important to create student group and apply skill to those, but not this way. Similar to how we do standard mapping, map entire list to students." |
| T_SC_19 | **Admin setup: no edit on existing checklists — create new instead.** A skills checklist that is in use (has been assigned to students) must not be editable. If requirements change, the admin creates a new named checklist. The existing checklist remains unchanged — preserving what past students were assessed on. Design must not expose an "Edit checklist" action on active/assigned checklists. | Admin | Skills setup | P0 | Aarti (via Sankalp): "edit नहीं करो existing skills को… एक अलग list बनाओ." |
| T_SC_20 | **Course mapping: remove matrix/grid view — use filter-and-select instead.** The existing matrix view (skills × course offerings grid where you check each intersection) is explicitly not the design. Replace with: (1) select a skill, (2) filter courses by term/academic year, (3) multi-select courses to map to, (4) save. Skills can still be mapped to multiple courses (one-to-many), just not via a grid/matrix. | Admin | Course mapping | P0 | Sankalp: "We don't need a view like that. We just need a view: skill select करो, courses select करो, save कर लो." |
| T_SC_21 | **Multi-checklist reporting: segment by checklist.** When a program has multiple named checklists (e.g., Skills Passport 1, Skills Passport 2), the reporting page must allow filtering/segmenting by checklist.
