# Mobbin pattern research — Home (HY-01): first-run setup that becomes a status page, and "needs attention" queues

Date: 2026-10-09 · Tool: Mobbin MCP (`claude_ai_Mobbin`, web, deep mode, 4 screen searches plus 1 flow search plus 3 follow-ups; every image was viewed, not just its metadata). The `mobbin` server (`mcp__mobbin__*`) was not authenticated and was not used.
Companions: `docs/design/mobbin-evidence.md` (job types 1 and 2 already hold HoneyBook, Vanta, Remote, Adaline, Zendesk, Oyster, Gorgias, Wrike; **not repeated here**), `docs/build/contracts/HY-01-home.md` (consumes this).
Patterns only, no pixel copying. **None of these products is clinical education, credentialing for clinicians, or an accreditation tool.** Fit ratings are mine `[INFER]`: **Strong** = answers a requirement of the Home job, **Partial** = one idea transfers, **Weak** = does not answer the job. The target user is a nursing-program administrator who must configure 40 to 200 skills `[REQ §3]` `[CALL 09-23]` (call says "40-50 skills" in a Word, Excel or PDF list, line 112; the requirements doc says up to two hundred).

## Part 1: first-run setup checklist that becomes a calm daily page

The Home job, restated from the sources: the admin imports a list, then works through many unconfigured skills over days `[REQ IM-10]`, then returns weekly `[brief-v2 §0, INFER]`. Setup is long, interruptible and data-driven (a count that goes down), not a five-minute product tour.

**Honest read of Part 1.** Every reference is a one-off product tour for a small, fixed number of steps, finished in a session, with a progress bar as the main meter. Our job differs in three ways: (a) one step is a long, repeated, interruptible bulk job with a decreasing count `[REQ IM-10, IM-14]`; (b) completion must be **derived from library data**, never ticked, because a re-import adds unconfigured skills `[REQ IM-11]` and the requirement says part-configured must be "a visible state of progress rather than a silent gap" `[REQ IM-10]`; (c) the "go live" idea is an open decision `[OD-15]`, and Salesforce is evidence of the pattern, not of the answer.
**What no reference showed:** a setup list whose step status is a **live count over a bulk library** (the closest are Squarespace's per-section counts and the Attio "Needs review 3" group in `mobbin-remaining-surfaces.md` M-1). No reference showed setup and a live work queue coexisting on one page during setup (students may start submitting on configured skills while the rest is unconfigured). That overlap is our design.

**Honest read of Part 2.** Strong precedent exists for (a) a counted, labelled attention card whose counts link to a filtered list (Vanta, Deel) and (b) setup as the first row of the same list (Remote). Weak precedent for everything involving time (due, overdue, remind, expiry), which our scope excludes `[REQ §14]`. **No reference** covers a queue whose rows are derived from configuration completeness (unconfigured skills, unmapped skills, unadopted instructors) rather than from deadlines. That row grammar is ours.

## What this changes in the contract

1. Setup status is **derived**, never ticked and never dismissed into silence (rows 2, 6, 11 counter-examples; REQ IM-10).
2. Setup is the **first row of the same attention list** and also shows its own count-led detail (rows 1, 12), so setup and steady state share one layout instead of two pages.
3. Attention rows carry **a count, a label and a one-line reason**, link into a filtered list (rows 13, 14), and have **no time words** (rows 12, 17, 18 counter-examples).
4. Every empty queue says so and names the next action (rows 16, Oyster).
5. "Activate / Go live" appears as a seam only; Salesforce (row 3) shows the pattern exists but does not settle OD-15.
6. Attainment, leaderboards, rankings and "behind" lists do not appear on Home (rows 14, 16; `[CALL 09-23]` heatmaps are phase 2; OD-27 undefined).
