## ADOPT proposals (3 / 3 budget)

### ADOPT-1: Set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2` in settings.json env block

**Upstream evidence**: Agent SDK TypeScript CHANGELOG 0.3.217 — "Changed subagents to no longer spawn nested subagents by default (depth cap lowered from 5 to 1); set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to allow deeper nesting." Also — "Added a cap on concurrently-running subagents (default 20, override with `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`)."

**Status upstream**: GA (TS SDK 0.3.217 stable; mirrored in Claude Code stable).

**What it gives us**: our named subagents are confirmed leaf agents — `.claude/agents/verification-reviewer.md` and `.claude/agents/ds-conformance-reviewer.md` invoke zero nested Agent/Task calls. The default depth cap of 1 does not immediately break our architecture. However, `docs/governance/verification-discipline.md` Pattern G instructs sessions to "spawn Explore to grep-verify every claimed change." A future subagent at depth 1 that follows Pattern G internally would try to spawn Explore at depth 2, which is now silently refused. Setting depth to 2 is a one-line forward-safety measure.

**How to wire**: add an `env` block to `.claude/settings.json`:

```json
"env": {
  "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "2"
}
```

Add a row to `docs/governance/claude-practices.md` Subagents table:

```
| Subagent spawn depth cap (default 1 since TS SDK 0.3.217; concurrency cap default 20) | CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH=2 in settings.json env block | current | 2026-08-15 | TS SDK 0.3.217 changelog |
```

**Risk**: near-zero. Depth 1→2 expands the cap; no security gate is weakened. Rollback = remove the env block entry.

**Open question**: does `.claude/settings.json` accept a top-level `"env"` key on our current Claude Code version? The v2154-2157 ADOPT-2 (`OTEL_LOG_TOOL_DETAILS` env flag) was PROPOSED but is not visible in the current settings.json — status unclear. If rejected for schema reasons, fall back to `~/.zshrc` or the launchd plist `EnvironmentVariables` section.

### ADOPT-2: Wire `Notification` hook for `agent_completed` — two-step approach (re-elevated from v2186-2201 HOLD)

**Upstream evidence**: CC CHANGELOG 2.1.224 — "Added cross-session SendMessage: Claude Code sessions can now message each other, on any of your machines, with ListAgents to discover them." TS SDK 0.3.224 — "Added `subkind: 'peer-send-message'` to the `task-notification` member of `SDKMessageOrigin`." CC ~2.1.198 (captured in v2186-2201) — Notification hook fires `agent_needs_input` / `agent_completed` for background agents.

**Status upstream**: GA.

**Why re-elevated**: v2186-2201 HELD this because the `agent_completed` payload format was undocumented and wiring `subagent-stop.py` blind was risky. TS SDK 0.3.224 now confirms Notification events carry an `SDKMessageOrigin` with a `task-notification` member with a `subkind` discriminant — a structure we can safely parse against.

**What it gives us**: `SubagentStop` fires only for in-session subagents. Background-session subagents (default since CC 2.1.198) instead fire `Notification/agent_completed`. Our subagent-invocations log currently misses all background completions. Resolves the `Notification event` row in `claude-practices.md` Hooks table (currently `deferred (no current notification flow)`, last verified 2026-05-09).

**How to wire (two steps, apply in order)**:

Step 1 — capture mode (zero risk): add to `.claude/settings.json` hooks, after `SubagentStop`:

```json
"Notification": [
  {
    "hooks": [
      { "type": "command", "command": "python3 \"$CLAUDE_PROJECT_DIR\"/.claude/hooks/notification-capture.py", "timeout": 5 }
    ]
  }
]
```

Create `.claude/hooks/notification-capture.py`: reads stdin JSON, appends raw payload to a scratch log, exits 0. Launch a background subagent and inspect the log to confirm the `agent_completed` payload shape.

Step 2 — parse mode (after payload confirmed): fold the parsing logic into `subagent-stop.py` (or `_telemetry.py`), handling both `SubagentStop` and `Notification/agent_completed`. Update the `claude-practices.md` Notification row to `current`.

**Risk**: Step 1 is read-only. Step 2 must catch parse exceptions and exit 0 on failure. Rollback = remove the Notification block.

**Open questions**: (a) capture-log location — scratchpad with TTL, not `~/.claude/`, since it will contain session IDs/agent names; (b) confirm two-pass sequence — apply Step 1, review captured payload, then authorize Step 2.
